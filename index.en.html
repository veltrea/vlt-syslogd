Veltrea Syslog Server　v0.4.0

Syslog that doesn't mangle your text.

It decides the character encoding per message, not per stream, and shows you which encoding it used. One file, no installer, no network, no admin rights.

One datagram UDP 514 RFC 3164 framing, UTF-8 payload

What arrived on the wire
3c 31 33 32 3e 61 75 74 68 3a 20 e8 aa 8d e8 a8 bc e3 81 ab e5 a4 b1 e6 95 97 e3 81 97 e3 81 be e3 81 97 e3 81 9f 3a 20 …
A receiver locked to one encoding
<132>auth: 隱崎ｨｼ縺ｫ螟ｱ謨励＠縺ｾ縺励◆: 繝ｦ繝ｼ繧ｶ繝ｼ admin
What vlt-syslogd shows
認証に失敗しました: ユーザー admin (3 回目)Enc: UTF-8

The decision is made for each datagram, so a Shift_JIS appliance and a UTF-8 appliance can share the same port and both stay readable. The encoding it settled on appears in the Enc column, so you can judge whether to trust what you are reading.

What it decides the encoding from

Guessing is the last resort, not the first. A declared charset wins; a BOM comes next; only then does it infer from the bytes. The Enc column names which of those actually happened.

Wire format, how the encoding is decided, and what the Enc column shows
What arrived How it decides Enc column
RFC 5424 with structured data charset="Shift_JIS" Takes the declaration at its word. A BOM is stripped if present, but never required. Shift_JIS (MSG-SD/BOM-Missing)
RFC 5424, no declaration, BOM present Reads it as UTF-8 on the strength of the BOM. UTF-8 (MSG-UTF8/BOM)
RFC 5424, neither declaration nor BOM UTF-8 if the bytes are valid UTF-8; otherwise inferred from the bytes. UTF-8 (Implicit) / Shift_JIS (Guess)
RFC 3164 (<PRI>Aug 01 19:37:14 host tag: …) Inferred from the payload bytes. UTF-8 / Shift_JIS
Bare BSD framing (<PRI>tag: …, no timestamp, no hostname) Accepted as-is; the word before the colon becomes the tag. UTF-8 / Shift_JIS

Real devices are not reliably standards-compliant, which is why the rule here is accept a wide range of shapes, and be explicit about how you read them. The original bytes are kept, so any row can be copied back out as hex with Copy as Hex.

One engine, three shapes

The part that reads syslog is the same code in all three. If you are not sure, start with Portable.

Portable vlt-syslogd-portable

A self-contained GUI that opens the UDP socket itself. Double click it and it is already receiving. No installer, no service registration, no internet.

This is the shape for a laptop you carry to a site, a borrowed machine at a customer, and the "I need ten minutes of logs" case.

none (Windows)

no

Server vlt-syslogd-srv

The headless engine. Registered as a Windows service, a launchd daemon or a systemd unit, it starts with the machine, writes what it receives to disk and streams it to Console.

This is the shape for a machine that must not miss anything.

admin, at install only

Console vlt-syslogd-console

The GUI that attaches to a running Server over TCP. Open it when you want to look; closing it does not stop collection. Starting, stopping and reconfiguring the service happens from here too.

The stream (5141) and control (5142) channels are loopback-only by default and protected by a shared token.

Three moves to a first log line

  1. Unzip and open it

    Portable needs no installation. Unzip and double click vlt-syslogd-portable.exe. If SmartScreen appears, choose "More info" then "Run anyway".

  2. Check the first row

    Listening on 0.0.0.0:514 (UDP) as the first row means the socket is open. If it failed, pick another port in Preferences.

  3. Send yourself one message

    A row should appear immediately.

    $u = New-Object System.Net.Sockets.UdpClient
$b = [Text.Encoding]::UTF8.GetBytes('<132>auth: login failed')
$u.Send($b, $b.Length, '127.0.0.1', 514) | Out-Null; $u.Close()

    Making it resident, or receiving from other devices, is covered in the manual.

Three things worth knowing first

These are where people usually get stuck.

514 is a privileged port on macOS and Linux

Ports below 1024 need root. On macOS (Mojave and later) 0.0.0.0:514 does not, but binding a specific interface such as 127.0.0.1:514 still does. On Linux you need root or CAP_NET_BIND_SERVICE. Moving to a port above 1024 avoids the whole question.

The macOS builds are ad-hoc signed, not notarized

There is no Apple Developer account behind this project, so Gatekeeper stops the first launch. Right click → Open once, or clear the quarantine flag with xattr -dr com.apple.quarantine. The Portable variant keeps its data next to the .app, and App Translocation breaks that while the quarantine flag is still there.

"Service running" is not "port reachable"

A running Server with a firewall in front of UDP 514 receives nothing at all. When remote logs do not arrive, check in this order: is bind_addr something other than 127.0.0.1, is the firewall open, and is the sender actually pointed at this machine.
